# 글 작성 지침 (공문형 · 도식 · 화면)

WorkBlog 에 업무 문서를 올릴 때의 **형식 · 흐름 · 기재 방식** 기준입니다. 새 문서를 쓸 때마다 이 지침을 따르고, 더 나은 방식이 생기면 이 문서를 먼저 고칩니다.

- 최종 갱신: 2026-10-27 (ACROSS 포털 사용 지침 작성 경험 반영)
- 적용 예: `ACROSS > Portal` 카테고리의 「ACROSS 포털 사용 지침」

## 1. 작성 흐름 (Flow)

1. **원본 확보** — HTML·Word·Excel·Markdown 원본을 서버에 올려 `파일 가져오기`로 초안 글을 만든다. 원본 사진은 자동으로 첨부가 된다.
2. **구조 설계** — 아래 2절의 공문 골격에 원본 내용을 배치한다. 빠진 정보가 없는지 원본과 대조한다.
3. **문장 다듬기** — 3절 기재 방식대로 짧게 줄이고, 길면 번호로 쪼갠다.
4. **도식 추가** — 흐름·구조·상태·검사 규칙처럼 글로 길어지는 부분은 4절 기준으로 도식을 만든다.
5. **화면 배치** — 5절 기준으로 캡처 크기와 번호를 맞춘다.
6. **검수** — 6절 체크리스트로 도식·화면을 한 장씩 확인한다. 겹침·잘림·찌그러짐이 하나라도 있으면 고친다.
7. **반영** — 기존 글이면 `PATCH`(또는 CLI `update`)로 본문을 교체하고 `changeNote` 에 무엇을 바꿨는지 적는다. 이전 내용은 변경 이력에 남는다.
8. **지침 갱신** — 이번에 새로 정한 규칙이 있으면 이 문서에 추가한다.

> 원칙: 업로드·변환·실행은 서버에서 한다. 개발 PC 는 도식 렌더링과 파일 전송까지만 한다.

## 2. 문서 골격 (공문형)

| 순서 | 구성 | 내용 |
|---|---|---|
| 머리 | 기관명 · 제목(가운데) | 예: "ACROSS 포털 운영" / "ACROSS 포털 사용 지침" |
| 머리 표 | 문서번호 · 시행일자 · 수신 · 참조 · 발신 · 제목 | 2×4 표. 문서번호는 `조직-주제-연도-일련번호` |
| 1 | 관련 | 근거 문서·화면 기준일 |
| 2 | 목적 | 2~3개 항목 |
| 3 | 적용 범위 | 한 줄 |
| 4~ | 본문 | 개요 → 권한 → 절차 → 준수 사항 → 조회 → 상태 정의 → 조치 요령 |
| 끝 | 협조 요청 | 이용자가 지켜야 할 것 |
| 맺음 | `붙임 OO 1부.  끝.` | 붙임이 없으면 `끝.` 만 |
| 붙임 | 용어 정의 등 | 표 |

### 번호 체계

`1.` → `가.` → `1)` → `가)` → `(1)` 순서. 들여쓰기는 단계마다 한 칸(에디터의 들여쓰기 = 32px).

## 3. 기재 방식

1. **짧게** — 한 항목 한 줄. 두 줄이 넘으면 번호로 나눈다.
2. **명사형 종결** — "~함", "~됨", "~불가", "~필수". 서술형("~합니다")은 쓰지 않는다. 협조 요청만 "~바람".
3. **화면 글자 그대로** — 버튼·메뉴는 `[배포 작업]` 처럼 대괄호로 화면 표기와 똑같이.
4. **수행자·위치 먼저** — 단계 제목은 `작업 — 수행자, [위치]` 형식. 예: `7) 실행 — 관리자, [실행]`.
5. **표로 바꿀 수 있으면 표** — 권한·상태·오류 코드처럼 같은 형식이 반복되면 표. 표 제목은 `<표 N> 제목`.
6. **○ / ×** — 가능·불가 표는 기호로.
7. **화살표** — 순서는 `→`, 결과는 `→` 뒤에 명사. 예: "실패 → 다시 지정".
8. **원문 보존** — 계정·코드·명령은 줄이지 않는다. 코드 블록으로 그대로.

## 4. 도식

### 언제 넣나

1. 단계가 4개 이상인 절차 → **흐름도**
2. 여러 시스템·저장소가 얽힌 구조 → **구성도**
3. 상태가 3개 이상 바뀌는 것 → **상태 전이도**
4. 검사·판정 규칙 → **판정도**(입력 → 비교 → 통과/차단)

### 만드는 법

1. SVG 로 직접 그린다(손으로 좌표 지정). 블로그 본문은 SVG 를 지우므로 **PNG 로 렌더링**해 첨부한다.
2. 렌더링: 브라우저 헤드리스 스크린샷, **2배 해상도**(`--force-device-scale-factor=2`), 폭 1500px 기준.
3. 글꼴: 맑은 고딕. 제목 28px · 상자 제목 18px · 설명 14px · 라벨 13px.
4. 색: 네이비 `#0B2A5B`(기본 흐름) · 하늘 `#2F9BE3`(포털·자동) · 청록 `#0F9D8A`(통과·성공) · 주황 `#E07B00`(예외) · 빨강 `#D7263D`(실패·차단) · 회색 `#8A97A8`(선택·보조).
5. 역할은 상자 오른쪽 위 배지(관리자·담당자·전원). 같은 말이 상자 제목에 있으면 배지를 빼서 중복을 없앤다.
6. 구역(준비·반복·예외)은 연한 배경 띠로 묶고 구역 이름은 화살표가 지나가지 않는 쪽 모서리에 둔다.
7. 상자 설명은 한 줄, 길면 상자 밖 안내에 번호로.
8. 맨 아래 범례(선 색 · 점선 · 배지)를 둔다.
9. 캡션: `[도식 N] 제목`.

## 5. 화면 캡처

1. 캡션: `[화면 N] 화면 이름`. 번호는 문서 전체에서 이어서.
2. 크기: 전체 화면 80%, 창·대화상자 60%. 가운데 정렬.
3. 원본 HTML 에서 가져온 사진은 `width/height` 속성이 남아 세로로 늘어날 수 있다 → 본문 CSS(`height:auto`)로 막혀 있지만, 새로 만들 때는 `style="width:80%"` 만 쓴다.
4. 캡처는 기준일을 문서 "관련"에 적는다(화면이 바뀌면 문서도 고친다).

## 6. 검수 체크리스트 (도식·화면 한 장씩)

1. 글자끼리, 글자와 선, 글자와 배지가 겹치지 않는가
2. 라벨 배경이 선이나 상자를 가리지 않는가
3. 단어 중간에서 줄이 바뀌지 않는가
4. 화살표가 의도한 상자에 정확히 닿는가(시작·끝 위치)
5. 같은 의미는 같은 색인가(통과=청록, 실패=빨강)
6. 빈 공간이 크게 남지 않는가(남으면 안내 문구로 채우거나 줄인다)
7. 사진이 찌그러지지 않는가(가로세로 비율)
8. 번호(도식·화면·표)가 빠짐없이 이어지는가

## 7. 반영 방법

| 작업 | 화면 | API / CLI |
|---|---|---|
| 파일로 새 글 | 글쓰기 › 툴바 [문서] | `POST /api/posts/import` · `workblog.py import 파일` |
| 본문 교체 | 글 수정 | `PATCH /api/posts/{id}` · `workblog.py update ID --file 본문.html --note "…"` |
| 사진·도식 올리기 | 툴바 [사진] | `POST /api/files` · `workblog.py upload 그림.png` |

- 본문에 넣은 사진의 첨부 id 는 `attachmentIds` 에 함께 보낸다(빠지면 글에서 떨어진다).
- 제목·요약·태그도 문서 성격에 맞게 바꾼다(요약은 "대상 · 내용 · 문서번호").
